# ADR-001: Capas simples para persistencia; el punto de extensión de notificación ya cubre el próximo cambio conocido

## Estado
Aceptado — 2026-11-20

## Contexto
Tras integrar Chain of Responsibility, Strategy y Observer en el sistema de solicitudes de reembolso, corresponde decidir si el proyecto debe migrar a arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia y notificación) o mantenerse en capas simples.

Datos del proyecto que condicionan la decisión:

- No existe hoy ningún plan de cambiar el motor de base de datos (H2 en desarrollo, un único motor relacional en producción).
- Contabilidad sí anunció, para el próximo trimestre, una integración por API externa para el pago de las solicitudes aprobadas.
- `SolicitudReembolsoService` depende de `RepositorioSolicitudesJpa` y, para notificar, de la interfaz `ObservadorCambioEstado`.
- El criterio de la Guía (sección 6.2) indica que Hexagonal vale la pena en sistemas que sobrevivirán 3 años o más con cambios de infraestructura.

## Alternativas consideradas

1. **Hexagonal completa** (puerto `RepositorioSolicitudes` + adaptador JPA + puerto de notificación). Descartada: para la persistencia no hay un cambio de infraestructura previsto que la justifique; agregaría interfaz, adaptador y duplicación de pruebas sin un caso de uso.
2. **Capas simples en todo** (sin ningún punto de extensión para notificación). Descartada: el cambio de Contabilidad es real y tiene fecha; no tener un punto de extensión obligaría a modificar el servicio.
3. **Capas simples para persistencia y punto de extensión existente para notificación** (elegida).

## Decisión
Se mantiene arquitectura en capas simples para la persistencia: `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin interfaz de puerto intermedia. Un puerto de persistencia hoy sería una abstracción especulativa (YAGNI) sin ningún caso de uso que lo requiera.

Para la notificación no se introduce ningún cambio: `ObservadorCambioEstado` ya es el punto de extensión necesario, y `NotificadorContabilidad` puede reemplazar su implementación interna por una llamada a la API externa el próximo trimestre sin modificar `SolicitudReembolsoService` ni los demás observadores.

Los límites que sí existen se verifican de forma automática con ArchUnit en GitHub Actions (`ReglasArquitectura`).

## Consecuencias

**Positivas**
- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El único cambio de infraestructura con fecha conocida (integración de Contabilidad) ya tiene su punto de extensión listo.
- Menos código y menos pruebas que mantener.

**Negativas**
- Si en el futuro se necesita cambiar de motor de base de datos, el puerto de persistencia deberá introducirse retroactivamente; se acepta esa deuda técnica de forma consciente.
- La llamada a una API externa dentro de `NotificadorContabilidad` se ejecutaría de forma síncrona dentro de `cambiarEstado`; si resulta lenta o falla, habrá que decidir manejo de errores y asincronía en ese momento.
- Un revisor que espere simetría total (puertos en todas las dependencias externas) puede interpretar la asimetría como inconsistencia si no lee este ADR.

## Cuándo reconsiderar
- Se fija una fecha de migración de base de datos o se agrega un segundo almacenamiento.
- La integración de Contabilidad exige reintentos, colas o ejecución asíncrona (se evaluaría entonces un puerto de notificación propio).
